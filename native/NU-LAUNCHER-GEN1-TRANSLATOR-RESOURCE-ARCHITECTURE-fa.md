# معماری اجرایی لانچر N.U — پک نسل اول، مترجم چندنسلی و کنترل منابع

وضعیت: **قرارداد مهندسی و مبنای پیاده‌سازی**؛ قابلیت‌هایی که در بخش «وضعیت فعلی» صریحاً پیاده‌سازی نشده‌اند، آماده یا تأییدشده محسوب نمی‌شوند.

## 1. پک اول بازی‌ها

پک پیش‌فرض Generation 1 شامل سه شناسهٔ ثابت است:

- `nu.gen1.bubble-hunt` — Bubble Hunt
- `nu.gen1.mana-collector` — Mana Collector
- `nu.gen1.chaos-attack` — Chaos Attack

هر سه در نصب اولیه فعال‌اند. کاربر باید بتواند هر بازی را جداگانه از Library/Package Manager حذف و بعداً دوباره نصب کند. حذف بازی، ذخیره‌ها، پروفایل و داده‌های شخصی را حذف نمی‌کند؛ پاک‌سازی داده‌ها یک عمل جداگانه با تأیید صریح است.

منبع واقعی هر بازی، فایل‌های وابسته، نسخه، مجوز، هش و تست سازگاری باید قبل از اتصال اجرایی ثبت شوند. `NU-GEN1-PACK-MANIFEST.json` فعلاً شناسه‌ها و سیاست نصب را ثبت می‌کند؛ چون payloadهای سه بازی هنوز به بستهٔ Native متصل نشده‌اند، هیچ‌کدام در این commit به‌عنوان بازی قابل اجرا معرفی نمی‌شوند.

## 2. مترجم چندسطحی و افزونه‌ای

### زنجیرهٔ ترجمه
`Package → Signature/Hash Verify → Manifest Validate → Generation Adapter → Canonical N.U IR → Capability Broker → Runtime Host → Renderer/Input`

- **Package Validator:** قالب، اندازه، نسخه، مجوزها، dependencyها و امضا را بررسی می‌کند.
- **Generation Adapter:** برای هر نسل و در صورت نیاز هر بازی، افزونهٔ مستقل با نسخه و تست سازگاری خودش دارد.
- **Canonical IR:** نمایش میانی نسخه‌دار و مستقل از سیستم‌عامل؛ شامل رویداد ورودی، فرمان بازی، عملیات منطقی و فرمان‌های ترسیم محدودشده است.
- **Capability Broker:** دسترسی فایل، شبکه، صدا، ورودی و گرافیک را فقط از طریق APIهای مجاز و با مجوز بسته می‌دهد.
- **Runtime Host:** IR را با سقف دستور، زمان، حافظه و تعداد رویداد اجرا می‌کند.

مترجم هیچ‌گاه نباید مستقیماً DLL/EXE یا کد ناشناختهٔ بسته را اجرا کند. ترجمهٔ نسل قدیمی‌تر به IR استاندارد انجام می‌شود؛ IR وابستگی به Win32، DirectX یا یک GPU خاص ندارد.

### یادگیری الگو و میان‌بُر امن
1. مسیر کامل ترجمه در حالت تشخیصی، ورودی‌ها، نسخهٔ adapter، خروجی IR و هزینه را ثبت می‌کند.
2. الگو فقط وقتی کاندید میان‌بُر است که ورودی/شرایط، نسخهٔ بسته، نسخهٔ مترجم و نتیجه قابل بازتولید باشند.
3. الگو در فضای محدود و نسخه‌دار ذخیره می‌شود؛ cache شامل کد اجرایی بومی نیست.
4. میان‌بُر با اجرای مرجع مقایسه می‌شود؛ اختلاف نتیجه، نسخه یا checksum آن را بی‌اعتبار می‌کند.
5. تغییر بسته، مترجم، IR، تنظیمات مؤثر یا schema، cache مرتبط را invalidate می‌کند.
6. مسیر مرجع همیشه موجود است؛ خطای cache باید به ترجمهٔ کامل برگردد، نه رفتار حدسی.

**اصل:** الگوی تثبیت‌شده فقط هزینهٔ ترجمه/کالیبراسیون را کم می‌کند؛ مجوزها، سقف منابع و صحت خروجی را دور نمی‌زند.

## 3. Pulse، کالیبراسیون و تثبیت سقف

سه probe مستقل و قابل تعویض تعریف می‌شوند:

- **CPU probe:** تعداد هسته/پردازندهٔ منطقی، قابلیت affinity، زمان‌بندی، بار نمونه و محدودیت‌های قابل اعمال سیستم‌عامل.
- **Memory probe:** RAM فیزیکی/آزاد، سقف commit/process memory قابل اعمال، working set و فشار حافظه.
- **Graphics probe:** adapter/driver، APIهای قابل استفاده، حافظهٔ گزارش‌شده و روش محدودسازی واقعی درایور/پلتفرم، در صورت وجود.

هر Pulse باید timestamp، نسخهٔ probe، واحد اندازه‌گیری، خطای احتمالی و سطح اطمینان داشته باشد. اندازه‌گیری یک‌باره، ظرفیت قطعی سخت‌افزار را اثبات نمی‌کند؛ برای تثبیت باید چند نمونهٔ کوتاه، warm-up، بررسی نوسان و محافظت در برابر خطا انجام شود.

### ترتیب اجرا
1. درخواست **quiesce** به Runtime Host و مترجم‌ها: کار جدید متوقف، رویدادهای ورودی صف می‌شوند، عملیات جاری در مرز امن تمام می‌شوند.
2. probeهای CPU/RAM/GPU نمونه‌برداری می‌کنند. لانچر کل سیستم‌عامل را freeze نمی‌کند و نباید scheduler یا سرویس‌های حیاتی سیستم را متوقف کند.
3. Core ظرفیت قابل اتکا را محاسبه می‌کند و برای هر منبع «قابل اندازه‌گیری»، «قابل محدودسازی»، «صرفاً قابل تخمین» یا «پشتیبانی‌نشده» ثبت می‌کند.
4. سیاست پیش‌فرض هدف‌گذاری روی حداکثر ۵۰٪ ظرفیت **قابل تخصیص به N.U** است؛ نه ۵۰٪ کل سخت‌افزار یا منابع موردنیاز سیستم‌عامل. reserve سیستم‌عامل و safety margin قبل از محاسبه کسر می‌شوند.
5. هر adapter/host فقط سقفی را دریافت می‌کند که سیستم‌عامل واقعاً می‌تواند اعمال کند.
6. پس از تأیید اعمال محدودیت‌ها، صف رویدادها آزاد و اجرا از سر گرفته می‌شود.
7. کالیبراسیون مجدد فقط با دستور کاربر، تغییر سخت‌افزار/درایور/سیستم‌عامل، به‌روزرسانی مؤثر، یا تشخیص خطای بحرانی انجام می‌شود. کاربر باید بتواند درخواست recalibration بدهد.

### واقعیت محدودیت‌های پلتفرم
- CPU: affinity تعداد پردازنده‌های مجاز را محدود می‌کند، اما معادل سقف دقیق ۵۰٪ زمان CPU نیست. CPU rate control در همهٔ نسخه‌های Windows در دسترس نیست؛ اگر API پشتیبانی نشود، وضعیت «hard cap unavailable» اعلام می‌شود.
- RAM: working-set limit به‌تنهایی سقف کل تخصیص/commit نیست. باید محدودیت واقعی process/job در نسخهٔ هدف آزموده شود؛ در غیر این صورت فقط soft budget و پایش فشار حافظه مجاز است.
- GPU: API عمومی و مستقل از سازنده برای محدودکردن درصد مصرف GPU در تمام سیستم‌ها وجود ندارد. در نبود قابلیت معتبر درایور، فقط بودجهٔ تعداد/اندازهٔ منابع، نرخ ارسال فرمان و کاهش کیفیت رندر قابل اعمال است؛ نه ادعای GPU hard cap.
- Windows XP: مسیرهای API و ابزارهای کنترل منابع با سیستم‌های جدید یکسان نیستند. هر قابلیت باید در زمان اجرا probe شود و نتیجه به‌صورت capability اعلام شود.

اگر یک منبع hard cap ندارد، Core باید اجرای آن workload را با soft budget محافظه‌کارانه، محدودیت کیفیت/نرخ یا توقف امن مدیریت کند؛ نباید موفقیت جعلی گزارش کند.

## 4. کنترل مرکزی و سلسله‌مراتب

Core مالک سیاست است. زیرمجموعه‌ها حق ندارند سقف مرکزی را افزایش دهند:

`Core Policy → Resource Controller → Runtime Host → Game Adapter / Translator → Renderer`

هر پیام بین اجزا شامل شناسهٔ جلسه، نسل، نسخهٔ پروتکل، deadline، هزینهٔ تخمینی و budget باقی‌مانده است. بودجهٔ دستور/زمان/حافظه به شکل سلسله‌مراتبی تقسیم می‌شود؛ مصرف بیش از سقف باعث yield، کاهش کیفیت یا توقف کنترل‌شده می‌شود.

Quiesce به معنی توقف امن workloadهای N.U است، نه فریز کل سیستم. کنترلر مدیریتی باید همیشه مسیر resume/abort امن داشته باشد.

## 5. Package Manager و امضای بسته

برای نسل اول، قالب متنی/باینری اختصاصی کوچک و نسخه‌دار کافی است؛ طراحی زبان اجرایی جدید تا زمانی که نیاز و مزیت آن با benchmark ثابت نشده، به تعویق می‌افتد.

حداقل اجزای manifest:
- شناسهٔ ناشر و بسته، شناسهٔ یکتا، نام، نسل، نسخه و حداقل Host API
- hash همهٔ فایل‌ها، الگوریتم hash، امضای ناشر و شناسهٔ کلید
- فهرست dependencyها با نسخه/محدودهٔ سازگاری
- permission/capabilityهای درخواستی
- entry point منطقی (نه اجرای مستقیم فایل native)
- حداقل منابع، محدودیت اندازه و اطلاعات سازگاری
- مسیر ذخیرهٔ دادهٔ کاربر جدا از فایل‌های قابل حذف برنامه

چرخهٔ نصب: دریافت در staging → بررسی اندازه/مسیر → hash → امضا و trust policy → schema → dependency resolution → تست سازگاری → نصب اتمیک → ثبت inventory. ارتقا باید rollback داشته باشد. حذف بسته فقط فایل‌های متعلق به همان بسته را حذف می‌کند.

## 6. وضعیت واقعی در شاخهٔ فعلی

- موجود: Win32 native shell، NUVM/1 محدود، تست conformance پایه و installer آزمایشی.
- ثبت‌شده در این تغییر: شناسه‌ها و سیاست پک اول، قرارداد مترجم/IR/cache، قرارداد Pulse و محدودیت‌های قابل اعمال، قرارداد Package Manager.
- هنوز پیاده‌سازی نشده: payload و اتصال اجرایی سه بازی، Library uninstall/reinstall، translator adapters، canonical IR، pattern cache، سه probe کامل، hard capهای واقعی، package verifier/signature/dependency resolver.
- عدم ادعا: PE subsystem 5.01 به‌تنهایی سازگاری XP را ثابت نمی‌کند؛ هیچ تست انسانی یا GPU hard cap در این تغییر ادعا نشده است.

## 7. دروازه‌های تست ماشینی

1. Manifest: سه شناسه یکتا، هر سه default-enabled، uninstallable، save-preserving.
2. Translator: adapterهای نسخه‌دار، رد نسل/API ناشناخته، fallback مرجع در cache miss/corruption.
3. Pattern cache: تکرارپذیری، invalidation با تغییر نسخه/ورودی، عدم اجرای native code.
4. Pulse: خطای probe، نبود سنسور، دادهٔ ناقص و نوسان باید به حالت محافظه‌کارانه برسند.
5. Resource controller: اثبات جداگانهٔ requested/accepted/effective limit؛ تست باید شکست کنترل را تشخیص دهد.
6. Quiesce: رویدادها گم نشوند، timeout و abort امن باشند، OS freeze نشود.
7. Package manager: hash اشتباه، امضای نامعتبر، path traversal، dependency ناسازگار و نصب نیمه‌کاره رد شوند.
8. Uninstall: فایل برنامه حذف، save/profile حفظ، reinstall موفق.
9. Regression: NUVM/1 فعلی، installer و مسیرهای موجود بدون افت کار کنند.

## 8. ترتیب پیاده‌سازی

P0: تست/مدل manifest و package inventory؛ P1: اتصال واقعی سه بازی و نصب/حذف؛ P2: canonical IR و translator registry؛ P3: Pulse probes و capability report؛ P4: resource controller با hard/soft distinction؛ P5: pattern cache امن؛ P6: امضا، dependency resolver، rollback و fuzzing.

Generation 2 همچنان خارج از محدوده است و این تغییر آن را باز نمی‌کند.
