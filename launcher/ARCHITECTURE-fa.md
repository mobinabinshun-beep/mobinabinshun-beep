# N.U Launcher — سند یکپارچهٔ معماری و قرارداد اجرایی
**شناسه:** NU-LAUNCHER-ARCH-001  
**نسخه:** 0.1.0  
**تاریخ:** 2026-11-16  
**وضعیت:** طرح اجرایی اولیه؛ نیازمند build و human QA

## 1. تعریف محصول

N.U Launcher یک میزبان اجرایی مستقل است. بازی و افزونه در فضای محتوایی مدیریت‌شدهٔ لانچر اجرا می‌شوند؛ لانچر مسئول کشف، اعتبارسنجی، نصب، وابستگی‌ها، انتخاب runtime، بودجه منابع، lifecycle و گزارش خطاست. صفحه وب یا فهرست میانبرها به‌تنهایی لانچر محسوب نمی‌شود.

## 2. سلسله‌مراتب ثابت

1. **Platform Adapter:** ورودی سیستم‌عامل، پنجره، فایل، حافظه، شبکه، installer و اعلان‌ها.
2. **Launcher Host:** چرخه عمر برنامه، UI، کاتالوگ، نصب/حذف، به‌روزرسانی و recovery.
3. **Runtime Adapter Registry:** انتخاب runtime سازگار بر اساس پلتفرم، معماری CPU، ABI، نسل و قابلیت‌های لازم.
4. **Core Services:** کالیبراسیون، بودجه منابع، زمان‌بندی، storage، event bus، diagnostics و policy.
5. **Engines:** renderer، audio، input، scripting، physics و شبکه؛ هرکدام با API نسخه‌دار.
6. **Modules:** بازی، ابزار، افزونه و محتوای نسل‌دار که فقط از قرارداد رسمی استفاده می‌کند.

هیچ ماژولی حق ندارد مستقیماً سقف منابع هسته را تغییر دهد یا به حافظه/DOM ماژول دیگر دسترسی داشته باشد.

## 3. نسل در برابر ABI

- Generation مشخص می‌کند ماژول متعلق به کدام خط محتوایی/قوانین N.U است.
- ABI مشخص می‌کند ماژول چگونه با میزبان و موتور ارتباط می‌گیرد.
- Runtime version نسخهٔ موتور اجراکننده است.
- یک Generation می‌تواند چند ABI/runtime داشته باشد؛ یک ABI نیز می‌تواند چند Generation را میزبانی کند، مشروط به سازگاری اعلام‌شده.
- هیچ installer نباید نسل‌های آینده را با یک فهرست ثابت یا محدودیت بسته‌بندی مسدود کند.

## 4. قرارداد Manifest

هر بسته باید manifest نسخه‌دار داشته باشد: شناسه پایدار، نسخه معنایی، generation، پلتفرم‌ها، نقطه ورود، ABI، وابستگی‌ها، قابلیت‌های درخواستی، راهنمای منابع و digest. انتشار عملیاتی علاوه بر hash به امضای ناشر و زنجیره اعتماد نیاز دارد. نمونه schema در `protocol/nu-module-v1.schema.json` است.

## 5. چرخه نصب و فعال‌سازی

resolve manifest → validate schema → verify publisher signature → verify package digest → check platform/ABI/generation/capabilities → resolve pinned dependencies → stage download → scan/validate → atomic activation → retain last-known-good → rollback on failure.

کشف فهرست ماژول‌ها هرگز نباید کد ماژول را اجرا کند. نصب ناقص نباید نسخه سالم قبلی را overwrite کند.

## 6. چرخه عمر ماژول

`discover → validate → prepare → mount → run → suspend → resume → unmount → dispose`

هر ماژول باید شناسه namespace مستقل، host surface مشخص، eventهای مجاز، درخواست منابع و مسیر teardown داشته باشد. ارتباط بین ماژول‌ها از event bus/API نسخه‌دار انجام می‌شود، نه global mutable state یا دستکاری مستقیم UI.

## 7. قرارداد کالیبراسیون و کنترل منابع

کالیبراسیون startup کوتاه و کم‌هزینه است؛ stress test دائمی ممنوع است. منابع شامل CPU time، memory budget، render resolution، frame pacing، optional effects، network budget و storage quota هستند.

حلقه کنترل:
1. نمونه‌برداری محافظه‌کارانه با confidence و timestamp.
2. تعیین سقف پایدار و حاشیه اطمینان.
3. تقسیم بودجه به ماژول و موتور.
4. اندازه‌گیری عملکرد واقعی در حین اجرا، بدون benchmark مصنوعی.
5. کاهش تدریجی ویژگی‌های اختیاری در افت عملکرد.
6. افزایش تدریجی فقط پس از پایداری چند پنجره اندازه‌گیری.
7. توقف/تعلیق امن ماژول در عبور از محدودیت یا فشار سیستم.

ده سطح، ضریب‌های سیاستی نسبت به سقف پایدار هستند؛ Level 10 به معنی استفاده نامحدود از سخت‌افزار نیست. بازی نباید با پایین آوردن کیفیت بصری، قواعد، فیزیک، اقتصاد یا اعتبارسنجی را تغییر دهد.

## 8. ده سطح کارایی

سطوح 1 تا 10 در تنظیمات کاربر قابل انتخاب‌اند. حالت پیش‌فرض Auto است و لانچر سطح پایدار را انتخاب می‌کند. سطح دستی فقط می‌تواند سقف را مساوی یا پایین‌تر از سقف پایدار نگه دارد. ماژول‌ها تنها بودجه را درخواست می‌کنند؛ Core تصمیم نهایی را می‌گیرد.

## 9. استراتژی گرافیک و پس‌زمینه

نسخهٔ پایه فقط یک تصویر ثابت پس‌زمینهٔ اختیاری دارد؛ هیچ لایه، particle، blur، parallax، WebGL یا انیمیشن پس‌زمینه در پوستهٔ پایه وجود ندارد. تصویر هرگز نباید کنترل‌ها یا محتوای foreground را بپوشاند یا ورودی را بگیرد. نبود/خرابی تصویر باید به رنگ پس‌زمینهٔ ساده fallback کند. Renderer بازی از پس‌زمینه لانچر مستقل است و باید از قرارداد بودجه پیروی کند.

## 10. Windows XP و مرز سازگاری

پوسته Win32 با APIهای پایه می‌تواند هدف کامپایل XP SP3 x86 داشته باشد؛ اما این موضوع به معنی سازگاری runtimeهای مدرن نیست. IE8 آخرین IE رسمی XP است و با JavaScript/Web APIهای مدرن مورد استفاده در Generation 1 هم‌سطح نیست. Chromium/CEF قدیمی روی XP منسوخ و از نظر امنیتی نامناسب است. بنابراین:
- XP برای shell و ماژول‌های native/legacy می‌تواند هدف آزمایش باشد.
- اجرای بازی‌های HTML فعلی در XP تا زمان ساخت adapter سازگار، **پشتیبانی‌نشده/اثبات‌نشده** است.
- runtime adapter باید feature detection واقعی و policy امنیتی داشته باشد؛ fallback نباید به اجرای محتوای ناامن منجر شود.
- نسخه‌های جدید Windows می‌توانند runtime adapter جدیدتر و مستقل داشته باشند.

## 11. امنیت و جداسازی

DLL ABI v1 در پوستهٔ اولیه داخل فرایند بارگذاری می‌شود و sandbox نیست؛ فقط برای نمونه‌های مورداعتماد است. انتشار عمومی به process isolation، least privilege، امضای بسته، بررسی hash، محدودیت فایل/شبکه، IPC نسخه‌دار، crash containment و rollback نیاز دارد. Shadow DOM یا namespace به‌تنهایی sandbox امنیتی نیست.

## 12. ده تنظیم قابل نمایش به کاربر

1. حالت خودکار (پیش‌فرض).
2. سقف کارایی دستی 1 تا 10.
3. کالیبراسیون در هر شروع.
4. کالیبراسیون بی‌صدا.
5. نمایش/عدم نمایش انتخاب‌گر.
6. استفاده از پروفایل ذخیره‌شده.
7. کالیبراسیون جداگانه برای هر بازی.
8. سقف نرخ فریم.
9. کیفیت رزولوشن/رندر.
10. افکت‌های اختیاری و reduced motion.

این‌ها ترجیحات‌اند؛ خاموش‌کردن گزینه‌های ایمنی یا افزایش بودجه فراتر از سقف پایدار مجاز نیست.

## 13. نقشه راه اجرایی

- **P0:** پوستهٔ Win32، registry، ABI آزمایشی، پنجره محتوای داخلی.
- **P1:** نمونه DLL، lifecycle کامل، خطا و recovery، تست XP/Win7/10/11.
- **P2:** Runtime Adapter API و adapter وب مدرن برای Windowsهای پشتیبانی‌شده.
- **P3:** اتصال Generation 1 با قرارداد budget و save adapter؛ بدون تغییر در nu-engine.js محافظت‌شده.
- **P4:** package manager امضاشده، dependency resolver، atomic update، rollback.
- **P5:** جداسازی فرایندی، sandbox و adapters سایر پلتفرم‌ها.
- **P6:** release installer، امضای کد، uninstall/repair و تست انسانی.

## 14. وضعیت پذیرش

کد ثبت‌شده به معنی binary ساخته‌شده نیست. وضعیت فعلی: SOURCE-COMMITTED، BUILD-NOT-VERIFIED، XP-RUNTIME-NOT-VERIFIED، HUMAN-QA-PENDING، NOT-RELEASED. هر وضعیت باید مستقل گزارش شود.
